# 샘플 공문 대조 결과

- 팀 화이팅구리(1인팀) · 컴포지 아이템 · 2026-08-12
- 대상: 창업팀이 전달한 OCR 샘플 공문 6종, 창업팀 답변(산출물 제출 범위·호스팅 범위)
- 목적: 새로 받은 원본 증빙을 현재 구현과 대조해 고칠 것을 찾는다

> 원본 공문 파일은 창업팀 자료라 이 저장소에 넣지 않았다. 아래는 대조하며 확인한 사실만 적은 문서다.

---

## 1. 샘플 공문은 20건 CSV의 원본 증빙이었다

지금까지 20건은 CSV 한 줄로만 알고 있었다. 원본 공문을 받아 대조해 보니
예외 4건이 왜 예외인지가 문서 본문에 그대로 적혀 있었다.

| 원본 공문 | 담긴 항목 | 대응 |
|---|---|---|
| 가온푸드 공급단가 변경 안내 | 3건 | DOC-001 · DOC-009(동결) · DOC-010 |
| 바다원 수산물 공급가 조정 안내 **[재발송]** | 1건 | DOC-017 = DOC-018 |
| 푸른포장 거래명세서 | 2건 | DOC-015 · DOC-016 |
| 새봄식품 포장규격 변경 안내 | 1건 | DOC-019 |

### 예외 판정의 근거가 원본에 있다

- **DOC-016 적용일 공란** — *"투명리드500은 본사 협의 지연으로 적용일자 미정입니다.
  확정 후 별도 안내드립니다."* 같은 명세서 안의 종이보울500은 적용일자가 `2026-08-12`로 적혀 있다.
  **한 문서 안에서 한 항목만 값이 비는 경우**가 실제로 존재한다는 뜻이다.
- **DOC-018 중복 의심** — *"앞서 7월 24일자로 동일 내용을 안내드렸으나 일부 거래처에서
  수신되지 않아 재발송하는 문서입니다."*, *"본 안내는 7월 24일 발송분과 동일한 내용입니다."*
  공문 제목에도 `[재발송]`이 붙어 있다. 회신(2026-08-11)이 말한 "공급사 재발송" 상황 그대로다.
- **DOC-019 규격 불일치** — *"박스당 중량이 10kg에서 9kg으로 변경되며 공급단가는
  86,000원으로 동일합니다."* 단가는 그대로인데 중량만 줄어 kg당 실질 인상이 되는 케이스다.

### 하나의 문서에서 여러 항목이 나온다

가온푸드 공문 1장에 3개 품목, 푸른포장 명세서 1장에 2개 품목이 들어 있다.
공지(2026-08-09) §3의 *"각 행은 파일이 아니라 구매 증빙 항목"* 이 실제 자료로 확인됐다.
현재 구현은 행 단위로 처리하므로 이 구조와 어긋나지 않는다.

## 2. 제공 PDF는 스캔본이 아니라 텍스트 PDF다

샘플 PDF 4종의 내부를 확인했다.

```
1_다품목_공문_예시.pdf                      이미지 0개 · /ToUnicode 2개 · MalgunGothic
2_일부가격누락_공문_예시.pdf                이미지 0개 · /ToUnicode 2개
44_OCR샘플_가온푸드_단가변경공문.pdf         이미지 0개 · /ToUnicode 2개
44_OCR샘플_바다원_단가조정공문_재발송.pdf    이미지 0개 · /ToUnicode 2개
```

이미지가 하나도 없고 `ToUnicode` CMap이 있는 디지털 문서라, 실제로 전체 텍스트를 추출해 확인했다.
**추가 요건의 난이도가 우리가 가정하던 것과 다르다.** OCR 엔진이 필요한 일이 아니었다.

남은 어려움은 글자 인식이 아니라 **표 구조 복원**이다. 추출하면 이렇게 나온다.

```
품목  규격  단위  기존단가  변경단가  적용일자
토마토살사S/O4kg/PKPK32,00033,6002026-08-01
```

셀 경계가 사라지므로 글자 좌표로 행과 열을 되살려야 한다.
스캔 이미지가 섞여 들어오면 그때는 OCR이 필요하다. 이 판단은 README 지원 범위에 반영했다.

## 3. 신규 샘플 10건을 현재 구현에 넣어 확인했다

`1_다품목_공문_예시`(6품목), `2_일부가격누락_공문_예시`(4품목)의 값을 넣고 판정을 봤다.

### 확인된 것 — 형식 검증이 실제 케이스를 잡았다

```
PR-003  청양고추  박스  unit_mismatch  형식오류 1건  needs_review
PR-004  우동면    팩    unit_mismatch  형식오류 1건  needs_review
  변경단가(원) 값 "추후 안내"을(를) 정수로 읽을 수 없습니다. 원 단위 숫자만 있어야 합니다(예: 32000).
```

공문에 *"청양고추와 우동면은 변경단가 및 인상률 미확정 품목입니다"* 라고 적혀 있고,
표에는 변경단가 자리에 `추후 안내`가 들어 있다.
공지 §2가 말한 *"값은 있으나 정수·날짜 등 형식 해석에 실패"* 가 정확히 이 상황이다.
2026-08-12에 구현한 형식 검증이 이 케이스를 그대로 잡았다.

### 발견한 것 — 20건으로 실행되지 않던 경로가 있었다

신규 10건의 단위는 `봉`·`망`·`말`·`팩`·`캔`·`박스`로, 전부 표준 집합 밖이라
`unit_mismatch`로 분류됐다. 확인해 보니 **20건의 단위는 `PK`·`BOX`·`PO`와
복수 병기 `KG/단`뿐**이어서, "표준 집합 밖의 단일 단위" 분기가 한 번도 실행된 적이 없었다.

`docs/단위검증_테스트.csv`(10건)를 만들어 자체 테스트 8번 섹션으로 고정했다.
`박스`(BOX의 한글 표기), `pk`(소문자), `" PK "`(앞뒤 공백) 같은 경계 케이스를 함께 넣었다.

### 판단 — 한글 단위 매핑 사전은 넣지 않는다

`박스 → BOX`, `봉 → PK` 같은 사전을 두면 확인 대상이 줄어들지만 넣지 않았다.
명세가 표준 단위를 `PK`·`BOX`·`EA`·`PO`로 정했고, `1봉`이 몇 `PK`인지는 공급사만 아는
정보이며, 자동 환산은 명세가 금지하고 있다. 관찰값을 그대로 두고 사람이 판단하게 한다.
실무 적용 시에는 이 사전이 필요하며, 미구현 사항으로 README에 남겼다.

### 부수 확인 — 규칙 기반 정규화 경로가 실제로 동작했다

신규 10건은 사전 19종에 없는 품목이라 전부 규칙 경로를 탔다(`{ rule: 10 }`).
그동안 "20건 범위에서 검증되지 않은 코드"로 남겨 두었던 경로가 정상 동작함을 확인했다.
다만 사전이 20건에서 뽑은 19종뿐이라 새 품목의 정확도는 규칙 수준까지만 보장한다.

## 4. 창업팀 답변에 따른 인계 준비

산출물 제출 범위가 확정됐다.

| 시점 | 제출물 |
|---|---|
| 1차 심사 (~2026-08-16) | 접속 가능한 URL + 발표자료 |
| 1차 통과 후 인계 | URL + 소스코드 전체 + 실행 README + JSON·CSV 샘플 설명 |

> 1차 심사의 URL은 실제 파이프라인이 동작하는 상태여야 합니다.
> 결과 화면이 고정값(하드코딩)이거나 스텁 응답인 경우 심사에서 인정되지 않습니다.

이 조건은 자체 테스트 3번(문서ID 전면 변경 + 행 순서 반전)으로 이미 증명해 두었다.

인계 시 요청받은 3항목을 README에 반영했다.

| 요청 항목 | 우리 구현 |
|---|---|
| 로컬 실행 절차 + 환경변수 템플릿 | 실행 절차 기재. **환경변수가 없어 `.env.example`을 두지 않았다** |
| 외부 서비스 의존성 목록 | **외부 API·DB·인증·유료 서비스 모두 없음.** 런타임 의존성은 `next`·`react`·`react-dom` |
| 배포 절차 1페이지 | Vercel 임포트 → 설정 변경 없음 → `main` push 시 자동 재배포 |

옮길 비밀값도 연결할 백엔드도 없어서, 창업팀 인프라로의 이전에 별도 준비가 필요하지 않다.
파일을 읽고 판정하는 일이 전부 브라우저 안에서 일어나므로 증빙 데이터가 외부로 나가지 않는다.

## 5. 이 대조로 바꾸지 않은 것

- **예외 4종 탐지 규칙과 20건 정답표** — 공지가 변경하지 않는다고 명시했고, 이번 자료도
  기존 판정을 뒤집는 내용이 아니었다. 자체 테스트 1번으로 회귀가 없음을 확인했다.
- **PDF 입력 구현** — 추가 요건이며 필수 7개 중 JSON·CSV 내보내기와 수기 등록이 남아 있다.
- **한글 단위 매핑 사전** — 3절의 판단대로 넣지 않았다.
