# 구매 자료 검토함 (ComfoziAI 구매 증빙 인박스)

2026 스타트업 영그라운드 MVP 개발 해커톤 · 컴포지 아이템 · **팀 화이팅구리(1인팀)**

흩어진 구매 증빙을 항목별로 구조화하고, 사람이 확인해야 할 문제를 근거와 함께 표시한 뒤,
사람이 승인한 항목만 ComfoziAI가 받을 수 있는 JSON·CSV로 내보내는 검수 도구다.

> **컴퓨터가 스스로 합치거나 확인 완료로 처리하지 않는다.** 판단은 사람이 한다.

## 실행 방법

```bash
npm install
npm run dev          # http://localhost:3000
```

개발·검증에 사용한 환경은 Node `v24.14.1` · npm `11.11.0`이다. `package.json`에 `engines`를
지정하지 않았으므로 다른 버전에서의 동작은 확인하지 않았다. 그 밖에 따로 설치할 것은 없다.

```bash
npm run build        # 프로덕션 빌드
npx tsc --noEmit     # 타입체크
npx eslint .         # 린트
npx tsx scripts/verify-20.ts   # 자체 테스트 (12개 섹션)
```

자체 테스트는 저장소 상위 폴더의 `42_해커톤_업로드용_증빙20건_2026-08-04.csv`를 읽는다.
창업팀 제공 자료라 저장소에 포함하지 않았으므로, 이 파일을 저장소와 같은 상위 폴더에 두어야
테스트가 돈다. 우리가 만든 검사용 파일 3종은 `docs/`에 함께 넣어 두었다.

| 파일 | 검사 대상 |
|---|---|
| `docs/형식오류_테스트.csv` | 정수·날짜로 읽을 수 없는 값 10케이스 |
| `docs/단위검증_테스트.csv` | 표준 집합 밖의 단위 10케이스 |
| `docs/필수컬럼누락_테스트.csv` | 9개 필수 컬럼 중 3개만 있는 파일. 매핑 단계에서 걸러 어느 컬럼이 없는지 알려주는지 |

UTF-8 BOM이 붙어 있어 `utf-8-sig` 기준으로 처리한다. BOM을 제거하지 않으면 첫 컬럼명이
`﻿문서ID`가 되어 컬럼 조회가 전부 실패한다.

`.env` 파일이 필요 없고 `.env.example`도 두지 않았다. **읽어야 할 키가 하나도 없기 때문이다.**

말로만 두지 않고 배포본에서 실제로 확인했다. 20건 파일 업로드 → 검수 메모 작성 →
예외 수용 승인까지 마친 뒤 브라우저가 주고받은 요청 전량을 확인한 결과는 다음과 같다.

```

전부 자기 도메인(hwaiting-guri.vercel.app) GET
```

소스 전체에도 `fetch`·`XMLHttpRequest`·`WebSocket`·`navigator.sendBeacon` 호출이 하나도 없다.

## 처리 흐름

```
CSV/수기 입력 → 9개 필드 구조화 → 정규화 품목명 후보 → 예외 4종 탐지
   → 상태 결정 → 사람 검수(수정·승인·반려) → 승인분만 JSON·CSV 내보내기
```

### 관찰값과 수정값을 분리한다

파싱 결과(`observed`)는 절대 변경하지 않고, 사람이 고치는 값은 `current`에 따로 둔다.
덕분에 어느 값이 원본이고 어느 값이 사람이 고친 값인지 항상 구분되며,
변경 이력(`change_log`)은 두 값의 차이로 남는다.

| 파일 | 역할 |
|---|---|
| `src/lib/types.ts` | 도메인 타입, 필수 컬럼·표준 단위·중복 키 상수 |
| `src/lib/dictionary.ts` | 품목명 매핑 사전, 약어·수량꼬리 규칙 |
| `src/lib/normalize.ts` | 정규화 후보 생성 (사전 → 규칙 → 데이터 부족) |
| `src/lib/detect.ts` | 예외 4종 탐지, 중복 그룹 판정 |
| `src/lib/parseCsv.ts` | BOM 제거, RFC 4180 파서, 필수 컬럼 검증 |
| `src/lib/pipeline.ts` | 전체 파이프라인, 상태 결정, 승인 가능 판정 |
| `src/lib/pdfExtract.ts` | PDF 표 구조 복원 (추가 요건) |
| `scripts/verify-20.ts` | 20건 자체 테스트 |

## 판정 규칙

| 예외 | 판정 조건 | 상태 |
|---|---|---|
| `missing_required` | 필수 9개 필드 중 하나라도 공란·공백 | `needs_review` |
| `spec_mismatch` | 규격이 `^\s*기존\s*(.+?)\s*/\s*변경\s*(.+?)\s*$` 에 매칭 | `on_hold` |
| `unit_mismatch` | 단위가 표준 집합(`PK`·`BOX`·`EA`·`PO`) 밖이거나 `/`·`,`로 복수 병기 | `on_hold` |
| `duplicate_suspected` | 7필드 키 완전 일치, 문서ID 오름차순 그룹의 2번째 이후 | `on_hold` |

상태 결정은 다음 순서다.

```
형식 오류 있음 또는 missing_required 있음   → needs_review
없고 spec/unit/duplicate 중 하나라도 있음   → on_hold
아무 문제 없음                              → new (승인 가능)
```

- 필수값이 비어 있으면 **채우기 전까지 승인 버튼이 비활성**이다.
- **예외가 남은 채로 승인하려면 검수 메모에 판단 근거를 적어야 한다.** 전체팀 공지(2026-08-09) §1의
  *"아무 검토 없이 예외 상태를 승인하는 흐름은 허용하지 않습니다"*, *"현재 값을 그대로 수용해
  승인하면 `exception_flags`와 승인 사유를 함께 보존합니다"*를 따른 것이다. 사유를 보존하려면
  사유가 있어야 한다. 값을 고치거나 "중복 아님"으로 되돌려 **예외를 해소한 경우에는 요구하지 않는다.**
- **승인한 뒤 값이나 근거가 바뀌어 승인 조건을 잃으면 승인이 풀린다.** 그 승인은 바뀌기 전
  상태에 대한 판단이었기 때문이다. 조용히 풀리지 않도록 변경 이력에 `승인 해제`로 남기고,
  값을 정상으로 되돌려도 자동으로 다시 승인하지는 않는다. 승인은 사람이 다시 누른다.
- 사람이 "중복 아님"으로 되돌리면 중복 플래그를 상태 계산에서 제외해 정상 흐름으로 복귀시킨다.
- **규격 판정과 단위 판정은 서로 배제하지 않는 독립 검사다.** 규격이 `기존 … / 변경 …`
  패턴이어도 단위가 표준이면 `unit_mismatch`는 붙지 않는다(DOC-019가 여기 해당).
- 자동 병합·자동 삭제·자동 승인·자동 환산은 하지 않는다.

### DOC-020 판단 근거

DOC-020은 규격(`기존 1kg / 변경 4단`)과 단위(`KG/단`)가 각각 독립 규칙에 해당하여
`exception_flags`에 `spec_mismatch`·`unit_mismatch` 두 개를 모두 담았다.
창업팀 회신(2026-08-06)으로 확인했으며, 규칙 명세 §6-2 표는 대표 유형 하나만 기재된 것이었다.
`review_status`는 `on_hold`.

## 값 형식 검증

예외 4종과 **별도 축**이다. 창업팀 회신이 *"예외 4종 탐지 규칙과 제공 20건 정답을
변경하지 않습니다"*라고 명시했으므로, 5번째 플래그를 만들지 않고 `format_errors`
배열에 따로 담는다. `exception_flags`는 그대로 4종이다.

검사 대상은 **정수·날짜로 해석해야 하는 3개 필드**다. 공지 2절이 지목한 범위가 그것이다.

나머지 6개는 검사하지 않는다. 명세에 `문서ID = DOC-###`, `원본유형 = PDF|XLSX|IMAGE|수기`처럼
형식이 적혀 있지만, 이건 제공된 합성 20건의 표기이지 제품 규칙으로 굳힐 근거가 없다.
실제 공급사마다 증빙 번호 체계가 다르고, 여기서 형식을 강제하면 20건 밖의 정상 데이터를
거부하게 된다. 단위는 `unit_mismatch`가 표준 집합 대조를 따로 맡는다.

| 필드 | 통과 조건 | 통과 예 | 실패 예 |
|---|---|---|---|
| `기존단가(원)` `변경단가(원)` | 천단위 콤마를 뗀 뒤 `^\d+$` | `32000` · `32,000` | `삼만원` · `33600원` · `32000.00` |
| `적용일` | `YYYY-MM-DD` 이면서 달력에 실재하는 날 | `2026-08-01` | `2026/08/01` · `2026-13-45` · `2026-02-30` |

- **읽기를 중단하지 않는다.** 회신 2절대로 파일 전체를 계속 읽고, 해당 행만
  `확인 필요`로 보내면서 실패 이유를 화면에 남긴다.
- **한 행에서 여러 필드가 실패하면 전부 모은다.** 첫 실패에서 멈추지 않는다.
- **공란은 검사하지 않는다.** `missing_required`가 이미 잡은 문제를 두 번 표시하지 않기 위해서다.
- **자동 보정을 하지 않는다.** `32.000`이 3만 2천인지 32인지 값만 봐서는 알 수 없고,
  단가를 잘못 읽으면 계약 금액이 틀어진다. 판단은 담당자에게 넘긴다.
- 원 단위 단가라 **소수점과 음수는 받지 않는다.** `32000.00`은 실패 처리된다.
- `2026-02-30`처럼 형식은 맞지만 달력에 없는 날은, 파싱 결과를 원래 숫자와 다시
  대조해 잡는다.

### 형식 오류도 승인을 막는다 — 명세를 넘어선 판단

명세와 회신은 형식 오류의 상태(`확인 필요`)와 표시만 지정했고, 승인 차단까지는
지정하지 않았다. 그럼에도 막기로 한 이유는, 단가를 정수로 읽지 못한 채 승인하면
내보내기에서 숫자 필드를 채울 수 없어 **앞단 설계가 받을 수 없는 출력이 나가기**
때문이다. 빈 값과 해석 불가 값은 "쓸 수 없는 값"이라는 점에서 같아서 같은 취급을 했다.

값을 고치면 즉시 풀린다. 영구 차단이 아니다.

## 정규화 품목명 — 사전을 사용했다

**품목명 매핑 사전(19종)을 품목 마스터로 사용한다.** 창업팀이 제공한 20건 기준 사전이며,
`src/lib/dictionary.ts`에 JSON 형태로 두고 조회한다.

조회는 3단이다.

1. **사전 조회** — 원문 품목명으로 찾는다
2. **규칙 기반** — 사전에 없으면 약어 전개(`냉감튀`→`냉동 감자튀김`, `S/O`→`소스`, `BBQ`→`바비큐`),
   수량·규격 꼬리 제거, 공백 정리를 적용한다
3. **데이터 부족** — 후보를 만들지 못하면 빈칸이 아니라 `데이터 부족`으로 표시한다

사전은 **품목명으로 조회**하므로, 금지 대상인 "문서ID별 예외 결과 하드코딩"과는 다르다.
문서ID를 바꿔도 판정이 동일함을 자체 테스트로 확인한다(아래 참조).

자동 정규화의 정확도는 평가 대상이 아니라는 안내에 따라, 후보를 표시하고
사람이 고칠 수 있게 하는 데까지만 구현했다.

## 출력 스키마

승인된 항목만 내보낸다. 승인 전·보류·반려는 제외된다.

```json
{
  "uid": "1:DOC-001",
  "doc_id": "DOC-001",
  "source_type": "PDF",
  "supplier_name": "가온푸드(예시)",
  "raw_item_name": "토마토살사S/O",
  "normalized_item_name": "토마토 살사 소스",
  "spec": "4kg/PK",
  "unit": "PK",
  "price_before": 32000,
  "price_after": 33600,
  "effective_date": "2026-08-01",
  "review_status": "approved",
  "exception_flags": [],
  "format_errors": [],
  "source_ref": {
    "input_method": "file",
    "file_name": "42_해커톤_업로드용_증빙20건_2026-08-04.csv",
    "row_no": 2
  },
  "reviewed_at": "2026-08-10T14:03:00+09:00",
  "review_memo": "",
  "change_log": [
    { "at": "2026-08-10T14:01:00+09:00", "field": "normalized_item_name",
      "from": "토마토살사소스", "to": "토마토 살사 소스", "action": "edit" }
  ]
}
```

| 필드 | 설명 |
|---|---|
| `uid` | **행을 유일하게 식별하는 값.** 명세 권장안에는 없지만 덧붙였다. 문서ID는 공문이 재발송되거나 파일을 두 번 올리면 중복되므로, 받는 쪽이 이 값을 키로 쓰면 안전하다 |
| `doc_id` | 원본 증빙 식별자. **유일하지 않을 수 있다** |
| `source_type` | 증빙이 원래 들어온 형태(`PDF`·`XLSX`·`IMAGE`·`수기`). 표시용 값이다 |
| `raw_item_name` / `normalized_item_name` | 공급사 표기 원문 / 정규화 후보 또는 사람이 고친 값 |
| `price_before` / `price_after` | 인상 전·후 단가. 동결·인하도 있다 |
| `review_status` | `new`·`needs_review`·`on_hold`·`approved`·`rejected` |
| `exception_flags` | `missing_required`·`spec_mismatch`·`unit_mismatch`·`duplicate_suspected` 순서로 담는다 |
| `format_errors` | 정수·날짜로 읽지 못한 필드(`field`·`value`·`reason`). 형식 오류가 있으면 승인이 막히므로 출력에서는 항상 빈 배열이다 |
| `source_ref.row_no` | 헤더를 1행으로 세는 1-indexed 행 번호 |
| `change_log` | 사람이 값을 고친 내역. 시각·필드·이전값·수정값·동작 |

### CSV 평탄화 규칙

CSV는 위 구조를 평탄화한다. 열 순서는 아래와 같고 인코딩은 UTF-8이다.

```
uid, doc_id, source_type, supplier_name, raw_item_name, normalized_item_name,
spec, unit, price_before, price_after, effective_date,
review_status, exception_flags, reviewed_at, review_memo,
source_input_method, source_file_name, source_row_no,
change_log_count, change_log_json
```

- **중첩 필드** `source_ref.*`는 `source_` 접두사를 붙여 편다(`file_name` → `source_file_name`).
- **`exception_flags`는 세미콜론(`;`)으로 잇는다.** 쉼표를 쓰면 열 구분자와 겹쳐 읽기 어려워진다.
- **`change_log`는 배열이라 열 하나로 펼 수 없어** `change_log_count`(건수)와
  `change_log_json`(JSON 문자열) 두 열로 남긴다. 건수만 두면 CSV만 받는 쪽이 이력을 잃는다.
- **맨 앞에 UTF-8 BOM을 붙인다.** 없으면 엑셀이 UTF-8을 인식하지 못해 한글이 깨진다.
- 값에 쉼표·따옴표·줄바꿈이 있으면 RFC 4180대로 따옴표로 감싸고 내부 따옴표는 두 번 쓴다.
- 줄바꿈은 `CRLF`.

## 지원 범위

**지원한다**

- CSV 입력(UTF-8, BOM 유무 무관), RFC 4180 따옴표·이스케이프 처리
- **화면에서 직접 등록(수기)** — 파일 인입과 같은 파이프라인을 탄다
- **PDF 공문에서 표 읽기** — 텍스트 PDF 한정. 좌표로 표를 복원해 후보를 만든다
- 9개 필드 구조화와 원본 파일명·행 번호 연결
- 정규화 품목명 후보 생성(사전 → 규칙 → 데이터 부족)
- 예외 4종 탐지와 사유·근거 원본 값 제공
- 상태 5종 결정, 중복 되돌리기, 승인 차단 조건

**지원하지 않는다**

- **XLSX 입력** — 요건이 "XLSX 또는 CSV 중 1개"라 CSV를 택했다. 필수 7개 완료 후 여유가 있으면 추가할 예정이다
- **스캔 이미지 PDF·EML 입력** — 추가 요건 중 PDF는 구현했다(위 `PDF 공문에서 읽기` 참조).
  다만 글자가 없는 스캔본은 OCR이 필요해 지원하지 않으며, 그런 파일이면 그 사실을 알려 준다.
  EML은 명세가 메일 계정 OAuth를 금지해 착수하지 않았다.
- **제공 20건을 벗어난 일반화** — 규격·단위 포맷이 20건 범위를 넘으면 파싱하지 않고 `확인 필요`로 떨어뜨린다
- 가격 판정·비교 리포트·협상·RFQ, 회원/권한, 기존 ComfoziAI Production·DB·API 연결

## 알려진 제약과 실패한 시도

- **정규화 규칙 기반 경로는 20건에서 실제로 쓰이지 않는다.** 제공된 20건이 사전 19종으로 전부
  커버되기 때문이다(자체 테스트 출력 `{ dictionary: 20 }`).
  2026-08-12에 받은 샘플 공문의 신규 품목 10건을 넣어보니 사전에 없는 이름이라 전부 규칙
  경로를 탔고(`{ rule: 10 }`), 후보 생성과 예외 판정이 정상 동작했다. 다만 사전이 20건에서
  뽑은 19종뿐이라, **새 품목의 정규화 정확도는 여전히 규칙 수준까지만 보장한다.**
- **표준 단위 밖의 단일 단위는 20건으로 검증되지 않았던 경로였다.** 20건의 단위는
  `PK`·`BOX`·`PO`와 복수 병기 `KG/단`뿐이라 "표준 집합 밖의 단일 단위" 분기가 한 번도
  실행되지 않았다. 샘플 공문에 `봉`·`망`·`말`·`팩`·`캔`·`박스`가 나와서
  `docs/단위검증_테스트.csv`로 이 경로를 따로 검사하도록 추가했다(자체 테스트 8번).
- **단위 표기를 자동으로 보정하지 않는다.** `박스`는 `BOX`의 한글 표기이고 `pk`는 `PK`의
  소문자지만, 둘 다 표준 집합 밖으로 보아 `unit_mismatch`로 분류한다.
  `1봉`이 몇 `PK`인지는 공급사만 아는 정보이고, 명세가 자동 환산을 금지하기 때문이다.
  실무에서 쓰려면 한글 단위 매핑 사전이 필요하며, 이는 구현하지 않았다.
- **관찰값은 완전한 원문이 아니라 앞뒤 공백을 다듬은 값이다.** CSV 파서가 셀을 읽는 시점에
  `trim()`을 적용하므로(`parseCsv.ts`), `" PK "`는 `observed`에 `"PK"`로 들어간다.
  화면의 "파일에서 읽은 원본" 문구는 이 범위에서 읽어야 정확하다. 셀 안쪽 공백과 그 밖의
  모든 문자는 손대지 않는다. 앞뒤 공백까지 근거로 삼아야 하는 검수는 지원하지 않는다.
- **DOC-020의 안내 문구(`1단 = 몇 kg인지 공급사 확인이 필요합니다`)는 규격의 `기존`/`변경` 값에서
  단위 토큰을 잘라 만든다.** 숫자를 뗀 나머지를 단위로 보는 단순한 방식이라, 단위 표기가 20건과
  많이 다르면 문구가 어색해질 수 있다. 이 경우 일반 문구로 대체된다.
- **자체 테스트 초안이 틀렸던 사례** — 하드코딩 검증에서 문서ID를 역순으로 매겼더니 중복 그룹의
  기준 항목이 바뀌어 FAIL이 났다. 확인해보니 "문서ID 오름차순 첫 건이 기준"이라는 명세대로 동작한
  것이었고, 구현이 아니라 테스트의 가정이 틀린 것이었다. 테스트를 (a) 순서 유지 (b) 순서 반전
  두 갈래로 나눠 각각 다른 것을 검증하도록 고쳤다.
- **파일 읽기에 실패해도 이미 검수 중이던 목록은 지우지 않는다.** 처음 구현은 실패 시 상태를
  통째로 비웠는데, 담당자가 잘못된 파일 하나를 고른 순간 진행하던 검수가 날아가는 동작이라
  오류 배너만 띄우고 목록은 유지하도록 고쳤다. 재검증 과정에서 발견한 결함이다.
- **빈 목록이 localStorage 백업을 지우던 결함** — 저장 로직이 "목록이 비면 백업 삭제"였는데,
  화면이 어떤 이유로든 빈 상태로 다시 뜨면 그 순간 백업이 지워졌다. 실제로 개발 중 화면이
  한 번 죽었을 때 검수하던 10건이 통째로 사라졌다. 삭제는 사람이 `비우기`를 눌렀을 때만
  일어나도록 고쳤다.
- **검수 메모가 저장되지 않던 결함** — 재업로드 대응으로 항목 키를 `uid`로 바꿀 때 메모 핸들러만
  `doc_id`를 넘기고 있었다. 핸들러 타입의 파라미터 이름이 `docId`로 남아 있던 것이 원인이라,
  이름을 `uid`로 바꿔 같은 실수가 반복되지 않게 했다.
- 상태는 브라우저 세션에 두고 localStorage로 백업한다. 요건상 영구 감사 로그·회원 권한이
  불필요하고, 심사 시 여러 명이 각자 접속해도 서로 간섭하지 않게 하려는 선택이다.

## 재업로드와 누적 인입

**파일을 다시 올려도 기존 목록을 덮어쓰지 않고 뒤에 이어 붙인다.**

중복 판정의 단위는 파일이 아니라 증빙 항목이고, 비교 범위는 "같은 파일 안"이 아니라
**이미 인입된 전체 항목**이다. 검수 대기·보류뿐 아니라 **승인 완료 항목도 비교 대상**에 포함한다.
공급사가 공문을 재발송하거나 담당자가 실수로 같은 파일을 두 번 올렸을 때,
같은 단가 인상이 두 번 반영되는 사고를 잡는 것이 이 기능의 목적이다.

| 항목 | 동작 |
|---|---|
| 내부 식별자 | `uid`(인입 순번 + 문서ID)를 문서ID와 별도로 둔다. 문서ID를 유일 키로 쓰면 재업로드에서 저장이 실패한다 |
| 기준 항목 | **시스템 인입 순서**(`intake_seq`)로 정한다. 먼저 들어온 항목이 기준이고 이후 인입분에 중복 의심을 붙인다 |
| 같은 파일 재업로드 | 내용 해시로 감지해 **안내 후 진행 여부를 사람이 선택**한다. 조용히 무시하지도, 조용히 넣지도 않는다 |
| 복수 플래그 상태 | `missing_required`가 포함되면 `needs_review`, 그 외 조합은 `on_hold` |

20건 파일을 두 번 올렸을 때의 결과는 다음과 같다. 1회차 20건은 판정이 바뀌지 않는다.

```
2회차 DOC-001~015·017·018  ["duplicate_suspected"]                                on_hold
2회차 DOC-016              ["missing_required","duplicate_suspected"]              needs_review
2회차 DOC-019              ["spec_mismatch","duplicate_suspected"]                 on_hold
2회차 DOC-020              ["spec_mismatch","unit_mismatch","duplicate_suspected"] on_hold
```

**한계**

- 파일 해시는 내용이 완전히 같을 때만 감지한다. 한 행만 고쳐 재송부된 파일은 해시가 달라
  안내가 뜨지 않는다. 다만 중복 탐지 자체는 행 단위로 돌기 때문에 같은 내용의 행은 그대로 잡힌다.
- 인입 이력은 브라우저 세션 범위다. 다른 기기·브라우저에서 올린 항목과는 비교되지 않는다.
- 이 동작은 **창업팀 회신(2026-08-11)의 제품 의도를 구현한 것으로, 채점 정답표(20건 1회 업로드)에는
  없는 범위**다. 정답표 기준 판정은 그대로 유지된다.

## 예시 데이터로 바로 보기

파일을 갖고 있지 않아도 **버튼 하나로 전체 흐름을 확인**할 수 있다.
심사는 배포 링크에 직접 접속해 이루어지는데, 파일이 없으면 빈 화면만 보게 되어
만들어 둔 기능을 확인시킬 방법이 없기 때문이다.

**결과를 미리 박아 둔 것이 아니다.** 앱에 CSV 문자열을 넣어 두고, 파일을 올렸을 때와
똑같이 파서에 통과시켜 같은 판정 경로를 태운다. 자체 테스트 11번에서 이를 확인한다.

> 1차 심사의 URL은 실제 파이프라인이 동작하는 상태여야 합니다.
> 결과 화면이 고정값(하드코딩)이거나 스텁 응답인 경우 심사에서 인정되지 않습니다.
> — 창업팀 답변 2026-08-12

예시 데이터(10건)에는 **예외 4종과 형식 오류가 모두 들어 있다.**

| 문서 | 담긴 경우 |
|---|---|
| SMP-004 | 규격 변경 통보 → `spec_mismatch` |
| SMP-005 | 표준 밖 단위(`봉`) → `unit_mismatch` |
| SMP-006 | 적용일 공란 → `missing_required` |
| SMP-007 | SMP-002와 내용 동일 → `duplicate_suspected` |
| SMP-008 | 변경단가가 `추후 안내` → 형식 오류 |

**창업팀이 제공한 20건은 넣지 않았다.** 해커톤 자료를 공개 URL에 실어 두는 셈이 되기
때문이다(규정 4번). 대신 같은 구조의 가상 데이터를 직접 만들었고, 덕분에
**20건이 아닌 데이터에서도 예외 4종이 잡힌다**는 것을 함께 보여준다.
예시 데이터 역시 문서ID를 바꿔도 판정이 같은지 테스트로 확인한다.

## 원본 행 원문

각 항목은 파일에 실제로 적혀 있던 **CSV 한 줄을 그대로** 들고 있고, 상세 화면에서 펼쳐 볼 수 있다.

```
SMP-004,PDF,바른물산(예시),냉동새우살,기존 1kg / 변경 900g,BOX,42000,42000,2026-09-05
```

관찰값은 앞뒤 공백을 다듬고 따옴표를 푼 뒤라 원문과 다를 수 있다. 검수 담당자가
"파일에 실제로 뭐라고 적혀 있었는지"를 확인할 수 있어야 근거가 되므로 손대지 않은 줄을 남긴다.

따옴표 안에 줄바꿈이 있으면 논리적 한 행이 물리적 여러 줄이 되므로, 파싱이 끝난 뒤에
원문을 다시 자를 수 없다. 파서가 행의 시작과 끝 위치를 기억해 두었다가 함께 돌려준다.
수기 등록 항목은 파일의 행이 아니므로 이 값이 비어 있고, 화면에도 표시하지 않는다.

`raw_line`은 내보내기 스키마에 넣지 않았다. 검수 근거이지 앞단이 받아 쓸 데이터가 아니다.

## PDF 공문에서 읽기 (추가 요건)

명세의 추가(선택) 요건이다. 필수 7개를 마친 뒤 착수했다.

> 원본 문서 입력을 한 가지 방식으로 추가하고 **후보 생성 가능성을 탐색**
> · OCR·AI 정확도 목표 없음 · **실패 사례와 미지원 형식 기록**

### OCR이 필요하지 않았다

받은 샘플 공문 4종을 열어 보니 **이미지가 0개인 텍스트 PDF**였다. 글자를 읽는 것은
문제가 아니었고, 진짜 과제는 **표 구조 복원**이었다. 텍스트만 뽑으면 이렇게 붙어 나온다.

```
품목  규격  단위  기존단가  변경단가  적용일자
토마토살사S/O4kg/PKPK32,00033,6002026-08-01
```

pdf.js가 글자 조각마다 위치를 함께 주므로, **y좌표로 행을 묶고 x좌표로 열을 갈라** 복원한다.

### 만드는 동안 걸린 것 세 가지

| 문제 | 원인과 처리 |
|---|---|
| 머리글 `품 목`을 못 읽음 | 자간을 넓힌 제목이라 `품`·`목` 두 조각으로 들어온다. **공백 조각의 폭**으로 자간과 열 경계를 갈라 합쳤다(자간 11pt 안팎, 열 사이 37pt 이상으로 뚜렷이 갈렸다) |
| `33,600`과 `2026-08-01`이 한 칸으로 뭉침 | 값끼리도 합치려 해서 생긴 문제다. 합치기는 **머리글 줄에서만** 하고 값은 좌표로 가른다 |
| 짧은 품목이 `번호` 열로 밀림 | `양파 중`(가운데 101)이 `품목명`(143)보다 `번호`(61)에 가까웠다. 칸 수가 머리글 수와 같으면 **왼쪽부터 순서대로** 짝지어 해결했다. 수가 어긋날 때만 좌표로 맞춘다 |

### 되는 것

샘플 공문 4종에서 **품목을 하나도 빠뜨리지 않고 읽는다.** 자체 테스트 12번이 이를 고정한다.

| 공문 | 표의 품목 | 읽은 수 |
|---|---|---|
| 다품목 공문(6품목) | 6 | **6** |
| 일부 가격 누락 공문(4품목) | 4 | **4** — `추후 안내`까지 그대로 |
| 가온푸드 단가변경 공문 | 3 | **3** — 적용일 포함 |
| 바다원 재발송 공문 | 1 | **1** |

읽은 값은 바로 쓸 수 있는 형태로 다듬는다. `32,000원` → `32000`처럼 콤마와 `원`을 떼어,
우리 형식 검증이 읽을 수 있게 한다.

### 안 되는 것

- **스캔 이미지 PDF는 읽지 못한다.** 글자가 없으면 그 사실을 알려 준다. OCR은 지원하지 않는다.
- **문서ID와 공급사는 채우지 않는다.** 표 밖(머리말·직인 옆)에 흩어져 있어 위치가 일정하지 않다.
  잘못 추측해 넣는 대신 비워 두고 화면에서 받는다.
- **적용일이 표에 없는 공문이 있다.** 다품목 공문은 적용일이 표가 아니라 본문의 `시행일`에 있어
  비워 둔다. 등록하면 필수값 누락으로 잡히고 담당자가 채운다.
- 표 머리글이 아는 이름과 다르거나, 한 칸이 여러 줄로 접히는 표는 읽지 못할 수 있다.

### 읽은 뒤에도 사람이 판단한다

추출 결과를 바로 목록에 넣지 않는다. 표로 보여 주고 값을 고칠 수 있게 한 뒤,
고른 것만 **파일·수기 등록과 같은 파이프라인**에 태운다. 읽어 왔다고 판정을 건너뛰면
PDF로 들어온 건만 중복 검사가 빠지는 구멍이 생긴다.

실제로 가온푸드 공문을 읽어 넣은 뒤 20건 CSV를 올리면, 같은 내용인 DOC-001·009·010이
중복 의심으로 잡힌다. 그 공문이 20건의 원본이기 때문이다.

## 수기 등록

파일이 없어도 화면에서 직접 넣을 수 있다. 공급사가 전화나 구두로 알려온 인상분을
담당자가 기록하는 상황이 이 기능의 용도다.

**별도 경로를 만들지 않고 파일 인입과 같은 파이프라인을 태운다.** 수기 등록만 따로 처리하면
"직접 넣은 건 중복 검사가 안 된다" 같은 구멍이 생기기 때문이다. 정규화 후보 생성,
예외 4종 탐지, 형식 검증, 중복 판정, 상태 결정이 모두 그대로 적용된다.

실제로 파일에 있는 DOC-001과 같은 내용을 수기로 등록하면 이렇게 뜬다.

```
MAN-002  [duplicate_suspected]  기준 DOC-001  on_hold
  2번째 인입분 DOC-001과(와) 내용이 모두 같습니다.
  같은 인상분이 두 번 반영되지 않도록 확인이 필요합니다.
```

- **출처는 `input_method: "manual"`로 남고 파일명·행 번호는 `null`이다.** 파일의 한 행이 아니므로
  비워 두며, 비어 있다는 것 자체가 "사람이 직접 넣었다"는 근거가 된다.
- **폼에서도 같은 검증기를 쓴다.** 값을 입력하는 동안 형식 오류를 바로 보여준다.
  규칙을 두 벌로 두면 파일 경로와 폼 경로의 판정이 어긋난다.
- **오류가 있어도 등록을 막지 않는다.** `확인 필요` 상태로 들어가고 목록에서 고치면 풀린다.
  적용일이 아직 미정인 공문을 먼저 기록해 두는 경우가 실제로 있어서다
  (창업팀 샘플 공문의 *"본사 협의 지연으로 적용일자 미정"* 이 그 사례다).

## 사람 검수 흐름

값이 바뀌면 판정도 다시 돌린다. 비어 있던 적용일을 채우면 `missing_required`가 풀리고
상태가 `승인 가능`으로 바뀐다. 정규화 품목명을 고치면 중복 그룹이 다시 계산된다.
중복은 목록 전체를 봐야 하므로 한 항목만 고쳐도 매번 전체를 다시 판정한다(`recomputeItems`).

- **승인** — 막히는 경우가 셋이다. ① 필수값 누락 ② 정수·날짜로 못 읽는 값 ③ 예외를
  수용하려는데 검수 메모가 비어 있음. 버튼을 비활성으로 두고 셋 중 무엇인지와
  무엇을 하면 열리는지를 버튼 아래에 적는다
- **반려 / 재검토** — 재검토는 상태를 되돌려 예외에 맞는 상태로 다시 계산한다
- **중복 아님으로 되돌리기** — 같은 품목을 같은 날 두 번 발주하는 정상 건이 있으므로,
  사람이 되돌리면 중복 플래그를 상태 계산에서 제외한다. 다시 중복으로 볼 수도 있다
- **검수 메모** — 판단 근거나 공급사에 확인할 내용을 적는 자유 입력란
- **변경 이력** — 값 수정·승인·반려·재검토·중복 판단 변경을 시각·필드·이전값·수정값으로 남긴다

자동 병합·자동 삭제·자동 승인·자동 환산은 하지 않는다. 모든 상태 변화는 사람이 누른 결과다.

## 진행 중

필수 요건 7개를 모두 구현했고, 추가(선택) 요건 중 **PDF 원본 문서 입력**까지 마쳤다.
남은 것은 스캔 이미지(OCR)와 EML이며, 이유는 `지원 범위`에 적었다.

완료된 것은 CSV 입력 파싱, **수기 등록**, 정규화, 예외 탐지, 값 형식 검증, 상태 결정,
검수 인박스·항목 상세 화면, 사람 검수 흐름과 변경 이력, 재업로드 누적 인입,
